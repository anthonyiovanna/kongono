# Progressive Architecture

> **Current through Phase 14G:** exact-current plan evidence may be executed by
> one directly supplied adapter through the optional bounded runtime. This adds
> no provider SDK, registry, workflow, or authority. The optional inert bridge
> can reduce one eligible normalized action suggestion through an exact trusted
> application mapping into proposal evidence. It is not a proposal port and
> performs no authority or effect. The optional application workflow binds one
> exact-current profile, deterministic inert wiring, and one direct adapter for
> one terminal operation. It does not call the bridge. The optional inspection
> leaf revalidates explicit supplied profile/wiring evidence without loading PHP
> and emits bounded inert Safe aggregate views. Phase 14H remains planned.

> **Phase 14C checkpoint context:** The optional neutral model-invocation contract
> and deterministic invocation-plan artifact packages are implemented. An
> application may opt into typed requests and privacy-preserving plan evidence
> without adopting provider execution. Raw messages are omitted from published
> plan bytes; plans, adapter labels, budgets, and digests grant no authority.
> Phase 14D runtime was planned at that checkpoint.

> **Phase 13 closed boundary:** The opt-in neutral Agent Principal contract,
> deterministic declaration artifact, deterministic admission, and synchronous
> one-operation runtime packages plus one exact-current Agent Application
> workflow and one optional visibility-safe read-only inspection leaf are
> implemented. Applications retain their
> existing direct framework paths. Admission plans are not grants and receipts
> are claims. No provider SDK, profile registry, command, autonomous loop,
> retained session, live monitor, or inspection authority exists. Phase 13H
> adds only root-owned external acceptance and the exact local checkpoint.

## Purpose

Kongono should let an application begin simply and adopt stronger boundaries as complexity grows without requiring a framework migration.

Agentic behavior is optional. Applications must remain buildable, testable,
diagnosable, documented, deployable, and operable without AI, a provider, an
account, or a network. An application may adopt the separate Phase 13B-13G
Agent Principal packages explicitly; later capabilities remain available only
through the separately authorized
[Phase 13 roadmap](phase-13-roadmap.md); existing framework use does not acquire
agent behavior or authority by implication.

Phase 13H validates the accepted stack from a root-owned external process. The
harness is test evidence, owns only temporary state, and changes no production
composition or authority. Phase 13 is closed. Phase 14A through 14G are
implemented as separate architecture, neutral-contract, deterministic
plan-evidence, runtime, bridge, application, and inspection boundaries.

Adopting Agent Inspection adds only deterministic Safe aggregate evidence. It
does not load or run the application, record projections, execute Chie/Hantei/
Oshie, repair state, reveal hidden data, or establish current authority.

## MVC at the edge

MVC is a friendly default for HTTP and UI concerns. Controllers may translate transport input, invoke application behavior, and produce transport output. Business logic must not be structurally trapped in controllers or depend permanently on the HTTP edge.

## Supported direction

The architecture will support applications organized with:

- MVC
- Actions or use cases
- Modular monoliths
- Domain-driven architecture
- Ports and adapters
- CQRS where justified
- Events
- Durable workflows

These styles are not mandatory layers, generated templates, or implemented APIs in Phase 0A. Their future integration must preserve explicit boundaries and shared Kongono invariants.

## Progression principle

Increasing rigor should be driven by application needs rather than framework ceremony. A small application should not pay the structural cost of a large system, while a growing application must have a path toward explicit modules, application actions, domain boundaries, and asynchronous or durable coordination.

## Invariants

Architectural flexibility does not authorize arbitrary framework behavior. Phase 0F now supplies only explicit interface-to-implementation constructor resolution with transient construction; autowiring, service scopes, and application-architecture conventions remain unselected. Phase 8E now supplies only deterministic Console result/help presentation and explicit one-write delivery; real commands, native process adaptation, executable behavior, and application integration remain unselected. Broader Application Graph knowledge, architecture validation, security metadata, telemetry, and other machine-readable contracts remain bounded by their current accepted state.

## Data progression

The completed Phase 6 Data Platform lets applications use explicit parameter-
bound SQL without requiring an ORM. Applications may progressively adopt
immutable SQL plans, deterministic migrations, optional generated Data Mapper
support, and operation-scoped integration as their needs justify each layer.

This progression does not authorize static database facades, ambient
connections, runtime service location, hidden lazy loading, request-time mapping
reflection or proxies, or Active Record as the framework core. Provider
capabilities, transactions, cleanup, and portability claims remain explicit.
Phase 6F implements the optional Experimental mapping build layer without
changing these invariants. Generated output is derived and not checked in; raw
SQL and typed plans remain first-class. Composition/lifecycle integration is
implemented by Phase 6G's outer database-application package without changing
the lower mapping or composition contracts. Phase 6 is complete at checkpoint
`f5903134e77bb2ecfaece6ee6b435a8ab2ecbd05`.

Phase 7A accepts Deterministic Persistence as one optional later progression
above those first-class paths. It keeps domain classes plain and application-
owned, mapping compiled before runtime, identity and change state operation-
scoped, flush and transaction authority explicit, and relationship load plans
bounded and visible. An application may continue using direct SQL or generated
Data Mapper repositories without installing persistence. Phase 7B now
implements the Experimental neutral `kongono/persistence` contract package.
Phase 7C adds the optional upper `kongono/persistence-build` package for one
strict application source, current mapping/domain validation, detached model,
and canonical provenance artifact. Phase 7D adds deterministic content-addressed
ordinary PHP state adapters with non-executing structural/current validation and
guarded publication. Applications may still stop at direct SQL or Data Mapper
repositories. Phase 7E adds one optional concrete single-entity operation
context over caller-owned database authority. Explicit flush executes at most
one change and uncertain failure releases all retained domain state. It adds no
generated-state loader, transaction owner, or SQL generation. Phase 7F adds the
separate repository source, explicit bounded one-level relationship/cascade
contracts, and generated stateless aggregate repositories. Command behavior
remains deferred; Phase 7G adds the optional exact-current generated loading and
Composition workflow.

## CLI progression

Phase 8A makes Structured CLI architecture an Accepted optional progression
above existing capabilities. Phase 8B adds the neutral `kongono/console`
contract package above API Metadata and Diagnostics. Phase 8C adds immutable
specifications and already-tokenized parsing plus the separate
`kongono/console-build` evidence layer. Phase 8D adds the optional
`kongono/console-runtime` execution layer with explicit handlers, cancellation,
reverse cleanup, and sequential isolation. Phase 8E adds the optional
`kongono/console-presentation` layer above Console with canonical human/machine
forms and explicit ports. Phase 8F adds the upper
`kongono/console-commands` capability layer with three exact read-only handlers
and generated Composition roots. Applications may continue to use lower
capabilities directly; no lower production package depends on the capability
layer. Phase 8G adds the upper `kongono/console-application` package and the
official one-shot `kongo` executable with exactly `application:build`.

Progression remains ordered: neutral definitions and invocation values,
bounded parsing and exact-current build evidence, operation-scoped execution,
human and versioned machine presentation, a first read-only command family, a
supported one-shot executable plus narrowly reviewed mutation, and external
acceptance. The sequence through the supported executable is implemented. Command
meaning, execution, and presentation remain separate.
Hidden host reads, runtime discovery, service location, hidden interaction,
false dry runs, direct handler output, and process-exit cleanup are rejected.

Phase 8G changes the topology from thirty-five to thirty-six packages and adds
only the supported process/application edge. `--plan` is non-mutating;
`--apply` explicitly authorizes contained, atomic, content-addressed,
no-clobber Composition publication. No prompt exists and `--no-interaction` is
automation-safe. Phase 8F snapshots remain programmatic rather than fabricated.
It changes no Application Graph or Composition schema, Kernel lifecycle, PHP
policy, or Stable API status. Phase 8H supplies root-owned external acceptance
and the exact Phase 8 checkpoint without changing that topology or production
authority. See the [Phase 8 external acceptance guide](phase-8-external-acceptance.md).

## Identity and access progression

Phase 9 follows the completed Phase 8 checkpoint as a separate optional
security progression. Phase 9A accepts doctrine and the fixed staged sequence
only. It adds no runtime or package. The ordered path is: neutral principal and
security-result contracts; explicit authentication orchestration; deterministic
deny-by-default authorization evaluation; operation-scoped Security Context and
Composition integration; one selected HTTP authentication/session and
protected-capability enforcement profile; one supported application workflow
with exact-current policy evidence; and external acceptance at the exact
checkpoint.

Each letter requires a separate architect directive. Applications cannot skip
the separation by treating a user record, principal kind, role, session, route,
middleware, binding, or command as permission. Authentication success is not
authorization, only exact `Permit` proceeds, enforcement belongs at the
protected capability, and immutable security state ends with one operation.
Future outer adapters may depend inward on neutral contracts; lower packages do
not depend upward. See the [Identity and Access Security guide](identity-and-access-security.md)
and fixed [Phase 9 roadmap](phase-9-roadmap.md).

## Observability and operational-evidence progression

Phase 10 follows the completed Phase 9 checkpoint as a separate optional
operational-evidence progression. Phase 10A accepts doctrine and fixes the
staged sequence without adding a package or runtime. It first separates
diagnostics, traces, metrics, operational events, security audit evidence,
authorization receipts, and product analytics; requires structured bounded
signals plus immutable operation-scoped context; and selects OpenTelemetry only
as an outer interoperability direction.

The fixed progression then permits only separately authenticated increments:
neutral contracts, tracing and validated propagation, bounded metric
aggregation, events and distinct audit evidence, one selected outer
OpenTelemetry bridge, one supported application workflow, and external
checkpoint proof. Dependency direction remains inward, Composition owns
lifecycle, and lower packages never depend on exporters. Context cleanup,
nondisclosure, cardinality budgets, explicit clocks/identifiers/sampling, and
bounded backpressure/failure semantics remain invariants throughout.

Phase 10B adds the Experimental `kongono/observability` neutral contract
package as the forty-fifth acyclic production package. Phase 10C adds the
Experimental `kongono/tracing` package as the forty-sixth. Phase 10D adds the
independent Experimental `kongono/metrics` package as the forty-seventh. Phase
10E adds separate Experimental `kongono/operational-events` and
`kongono/security-audit` siblings as the forty-eighth and forty-ninth packages.
All four signal packages depend only on Observability, API Metadata,
Diagnostics, and PHP; none has a production reverse dependency.
The package owns explicit optional correlation, bounded scalar attributes,
versioned signal identity, closed kind/status, one immutable envelope, and one
recorder interface without an implementation. Phase 10C adds exact typed IDs,
trusted typed propagation without a carrier parser, caller-owned
clock/identifier/sampling/recording, bounded root/child lifecycle and
attributes, deterministic Record/Drop observations, idempotent cleanup, and
overlap/reentrancy isolation. Phase 10D adds finite typed metric values,
schema-owned dimensions, 64-series instrument and 256-series plan bounds, four
exact instrument kinds, immediate aggregate-only state, deterministic metric
observations, and explicit Active/Collected/Retired cleanup. Dynamic labels,
raw measurement logs, generic log pipelines, exporters, backends, and
application integration remain unimplemented. Phase 10E adds finite event/audit
schemas, explicit distinct semantics, supplied-field disclosure, and visible
unretried recorder failure. Phase 10F requires separate authenticated authority.
See
[ADR 0114](../adr/0114-explicit-observability-and-operational-evidence-boundary.md),
[ADR 0115](../adr/0115-structured-signals-context-and-exporter-neutrality.md),
[ADR 0116](../adr/0116-neutral-observability-contracts-and-package-boundary.md),
[ADR 0117](../adr/0117-operation-scoped-tracing-lifecycle-and-typed-propagation.md),
[ADR 0118](../adr/0118-bounded-cardinality-metric-aggregation-and-explicit-collection-lifecycle.md),
[ADR 0119](../adr/0119-structured-operational-events-and-bounded-security-audit-evidence.md),
the [Observability and Operational Evidence guide](observability-and-operational-evidence.md),
and fixed [Phase 10 roadmap](phase-10-roadmap.md).

## Do not use this doctrine to

- Put all business behavior in controllers because MVC is supported.
- Introduce CQRS, events, or workflows without a justified application need.
- Create speculative abstraction layers for future scale.
- Bypass framework security, lifecycle, or metadata invariants.

## Phase 10E operational-evidence boundary

Phase 10E adds only separate Experimental Operational Events and Security Audit
sibling packages over the neutral Observability recorder. Finite schemas,
canonical typed values, supplied-field disclosure, explicit event severity and
status, audit outcome and retention intent, and `not_guaranteed` durability are
implemented without changing application architecture. The packages expose no
conversion API and grant no identity, authorization, policy, business, repair,
storage, retention, compliance, or application authority. The graph is exactly
forty-nine acyclic packages and 166 local edges. Phase 10F remains separately
authorized future work. See [ADR 0119](../adr/0119-structured-operational-events-and-bounded-security-audit-evidence.md).

## Phase 10F outer adapter boundary

Phase 10F adds only the fiftieth outer Experimental package,
`kongono/opentelemetry`. Earlier application architecture and lower signal
packages remain unchanged and do not depend on the adapter. One explicit upper
owner may construct the bridge with bounded resource, batching, time, clock,
and transport capabilities; there is no service location, global provider,
environment discovery, automatic wiring, or Kernel state. At the Phase 10F
checkpoint the graph had 169 local production edges.
See [ADR 0120](../adr/0120-explicit-opentelemetry-otlp-http-protobuf-bridge.md).

Phase 10G supplies the supported upper application boundary without changing
lower signal packages. Closed configuration becomes deterministic exact-current
evidence, then explicit construction supplies live collaborators. One bounded
application operation owns cleanup and signal routing; no container, global
provider, environment discovery, or hot reload is introduced. The graph has
182 local edges across 52 acyclic packages. Phase 10H closes the milestone at
checkpoint `6f7865dbacc7dd9c4b90d2b60bd229b89efbd535` with root-owned external
acceptance and no new production behavior.

## Phase 11A progressive Graph boundary

Phase 11A accepts the future authoritative Application Graph as an optional
machine-readable substrate without making it a prerequisite for direct use of
Kernel, Composition, HTTP, database, persistence, security, observability, or
the existing structural Graph. Small applications may keep using those lower
accepted boundaries while later separately authorized phases add Graph
production and consumption.

The future IR admits explicit producer records; the future Graph derives
validated canonical immutable facts for one exact application state. Stable
identity, typed vocabulary/schema, provenance, visibility, construction,
artifact currentness, inspection, and developer-intelligence derivation follow
the fixed [Phase 11 roadmap](phase-11-roadmap.md). No row starts automatically.

Phase 11A implements none of those mechanisms and does not change the Phase 0J
snapshot, introduce a package or command, or grant AI, extensions, or agents
authority. See the [Authoritative Application Graph guide](authoritative-application-graph.md)
and [ADR 0123](../adr/0123-authoritative-application-graph-and-language-neutral-ir-boundary.md).

Phase 14 closes with an optional provider-neutral stack and offline external
evidence. It adds no default provider, ambient registry, credential discovery,
automatic fallback, authority decision, or external effect. Applications remain
responsible for explicit adapters and policy. See [Phase 14 external
acceptance](phase-14-external-acceptance.md).
