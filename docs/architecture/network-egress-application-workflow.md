# Network-Egress Application Workflow

## Current status

Phase 15F and [ADR 0160](../adr/0160-exact-current-single-profile-network-egress-application-workflow.md)
are Accepted. The optional Experimental `kongono/network-egress-application`
package is implemented. Phase 15G and
[ADR 0161](../adr/0161-visibility-safe-network-egress-inspection-and-bounded-evidence.md)
are Accepted and add the optional Experimental
[`kongono/network-egress-inspection`](network-egress-inspection-and-evidence.md)
upper evidence leaf. Phase 15H external acceptance and checkpoint is Accepted,
and Phase 15 is closed. The production graph is 81 packages with 317 local
production edges and is acyclic. Inventories are 1,514 production PHP files,
768 package-test PHP files, and 84 root-test PHP files.

## Purpose and context

The package gives one application a deterministic composition workflow around
the accepted policy-artifact and runtime boundaries. It keeps build-time
currentness, generated wiring, explicit port selection, and application lifecycle
outside the Phase 15D runtime, whose responsibility remains one bounded operation
and opened-session cleanup.

## Use when

Use this package when an application owns one complete egress policy source and
exact artifact and wants one reviewable generated boundary for one synchronous
operation. The application must already own explicit resolver, transport,
authority-currentness, cancellation, and monotonic-clock implementations.

## Do not use when

Do not use it as a general HTTP client, DNS implementation, credential provider,
transport registry, provider adapter, retry or redirect engine, connection pool,
background worker, deployment manager, or compatibility certificate. It does not
select the Phase 15E cURL transport automatically and does not depend on that
package.

## Inputs

The build operation accepts one existing application-owned root, one relative
contained existing output directory, one complete `EgressPolicySource`, and the
exact policy artifact bytes. Starting accepts the exact loaded profile plus one
directly supplied `EgressResolver` and `EgressTransport`. Running accepts exactly
one operation, receipt identity, attempt identity, authority-currentness port,
cancellation port, and monotonic clock.

## Outputs

The build returns the exact-current profile, reconstructed generated-wiring
evidence, the published content-addressed path, and a one-use loaded handle. One
run returns the exact `EgressRuntimeResult` produced by Phase 15D. These are inert
claims, not authority or proof of delivery.

## Deterministic workflow

1. Phase 15C validates the supplied source and artifact as exact-current.
2. A bounded versioned canonical projection derives the profile identity.
3. Canonical strict PHP is generated and structurally validated.
4. Exact-current validation binds every generated identity and digest field to
   the in-memory profile before publication.
5. Publication creates one content-addressed file atomically without clobbering
   different bytes.
6. Loading snapshots, validates, loads once, and reverifies the explicit file.
7. Starting revalidates the profile and checks the explicit transport capability
   set before resolution or transfer.
8. Running creates one exact Phase 15D request, delegates to a fresh runtime, and
   retires permanently.

## Side effects

Build may create only the final generated PHP file in the explicit output
directory and temporary same-directory publication state that is removed before
return. Loading declares one generated class. Starting performs a transport
capability query but no resolution or transfer. Only Phase 15D may call the
resolver or transport and own an opened session.

## Security

Generated PHP and profile identities omit origins, URIs, addresses, headers,
bodies, credentials, tokens, cookies, CA material, artifact bytes, paths, resolver
output, and foreign messages. Diagnostics use closed Safe aggregate fields.
Containment rejects empty, absolute, drive-relative, traversal, control-bearing,
link, junction, reparse, and escaping publication paths within the accepted local
filesystem model. Exact-current evidence does not establish live authority or
external truth.

Loading trusted generated and in-process PHP is not sandboxing. The caller must
protect the root, generated path, source, artifact, ports, and operation input.

## Lifecycle and concurrency

The loaded handle starts once. The application moves Ready to Active exactly once
and always reaches Retired. Reentrancy, overlap, replay, and use after retirement
fail before another resolver or transport effect. Separate application instances
share no operational state. The package provides no asynchronous or background
execution.

## Failure behavior

Stale policy evidence, changed generated bytes, implementation mismatches, path
replacement, unexpected load returns or declarations, incompatible transport
capabilities, and lifecycle conflicts fail closed. Package exceptions expose
bounded diagnostics without foreign presentation. Exact `Error` identity is
preserved; non-`Error` operation failures retain the exact previous throwable.
Phase 15D result, uncertainty, and cleanup evidence remains inspectable through
that preserved failure chain.

## Performance

Profile and wiring work is bounded linear hashing and validation over finite
policy and generated bytes. Publication and loading perform bounded local file
reads plus metadata checks. There is no scanning, discovery, polling, network
probe, cache, retry, or benchmark claim.

## Developer example using fakes

```php
$build = (new NetworkEgressApplicationBuildWorkflow())->build(
    $applicationRoot,
    'generated',
    $policySource,
    $policyArtifactBytes,
);

$application = $build->loadedWiring()->start($fakeResolver, $fakeTransport);
$result = $application->run($runInput);
```

The example assumes application-owned test fakes and inert documentation inputs;
it does not resolve DNS or perform network I/O.

## Current and non-current claims

Current: exact-current policy validation, deterministic profile identity,
deterministic inert wiring, contained no-clobber publication, explicit one-path
load, direct resolver and transport supply, capability precheck, and one terminal
runtime operation.

Not current: a first-party resolver, automatic transport selection, credential
discovery, provider semantics, inspection command, compatibility certification,
Phase 15 checkpoint, Stable API, release, or production-readiness claim.
