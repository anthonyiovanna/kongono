# Trusted In-Process Extension Host

Phase 12H externally proves exact one-file loading, deterministic lifecycle,
operation isolation, retirement, reverse cleanup, and bounded failure evidence
without changing this host. Trusted in-process PHP is explicitly not sandboxed.
See [Phase 12 external acceptance](phase-12-external-acceptance.md).

## Purpose and current boundary

Phase 12F implements the Experimental `kongono/extension-host` package. It is a
bounded application and operation lifecycle for one exact Phase 12E generated
wiring file. It is not a general plugin system, sandbox, extension registry,
arbitrary dispatcher, package installer, marketplace, external process host,
or production-readiness claim.

## Calling contract

The caller supplies one exact `GeneratedExtensionWiringArtifact`, its exact
`ExtensionGrantPlan`, and the absolute path to the single expected generated
PHP file. The path must resolve to the same ordinary local file named
`<wiring-sha256>.php`. Before loading, the host revalidates artifact structure,
plan identity, file metadata, size, bytes, hash, and path safety. It performs no
directory scan, discovery, alias repair, selection, fallback, or retry.

One `require` occurs only after pre-load validation. The loader then uses
Reflection once to verify the exact generated application and operation class
shapes, hosted boundaries, ordered accessors, implementation classes, and
lifecycle interfaces. A post-require mismatch is visible and irreversible for
that process: declared classes are not unloaded and another file is not tried.

## Generated hosted boundaries

Extension Composition owns the lower
`GeneratedExtensionApplicationBoundary` and
`GeneratedExtensionOperationBoundary` interfaces. Generated classes preserve
their existing typed methods and add list-shaped hosted delegation:

- application providers are checked in exact generated order before direct
  delegation to the typed application `start()` method;
- operation providers are checked in exact generated order before direct
  delegation to the typed `beginOperation()` method; and
- application and operation extension lists preserve generated order.

These methods introduce no provider map, lookup by string, resolver, container,
autowiring, or caller-selected method dispatch.

## Lifecycle

`ApplicationExtensionInterface` has `start(): void` and `stop(): void`.
`OperationExtensionInterface` has `begin(): void` and `close(): void`.
Construction is distinct from lifecycle success. Only an extension whose
`start()` or `begin()` returned successfully enters the reverse cleanup set.

Host startup constructs the exact generated application assembly, starts its
application extensions in order, and rolls back successful starts in reverse
order on failure. A successful host can create fresh operations. Each operation
constructs a fresh assembly, begins extension instances in order, and closes
successful instances in reverse order. Before cleanup completes, the operation
detaches its assembly, extensions, and host reference. The application host
retains no operation assembly or operation extension instance.

Each live operation owns one lease. Sequential, overlapping, and reentrant
operations are supported without ambient state. Shutdown with active leases
fails before state mutation or cleanup. A closed operation releases its lease
once; repeated close is a no-op. Successful shutdown detaches application state
before reverse cleanup and repeated shutdown is a no-op. No destructor performs
lifecycle work.

## Failure and retirement

Cleanup continues after individual failures. If a primary failure exists, it
remains primary and cleanup throwable identities are retained in the bounded
combined failure. Without a primary failure, a single cleanup throwable is
reused unchanged and multiple cleanup failures use the deterministic combined
lifecycle failure.

Operation activation or cleanup uncertainty retires the host. Retirement
rejects new operations but preserves explicit application shutdown. Provider
count and provider type rejection occurs before extension lifecycle work and
does not retire an otherwise sound host.

## Security and disclosure

Trusted/in-process means trusted code running with ordinary PHP process power.
The host does not sandbox filesystem, network, environment, process, global,
static, autoload, or other PHP access. Capability provider edges bound only the
collaborators supplied by Kongono. Use a future separately authorized sandboxed
or external profile when process isolation is required.

Host diagnostics use fixed identifiers, titles, remediations, violation tokens,
states, and bounded counts. They do not present paths, class/interface names,
artifact or plan identities, generated bytes, provider values, credentials, or
native exception messages. Native throwable identity is preserved for trusted
programmatic inspection; native trace sanitization is not claimed.

## Performance and concurrency

Loading performs bounded file reads, hashing, validation, one `require`, and
one-time Reflection. Normal lifecycle paths are direct typed calls with no
runtime Reflection. The host provides deterministic in-process lifecycle
isolation, not thread safety or process isolation; callers remain responsible
for concurrency appropriate to their PHP execution model.

## Stability and deferred work

The package and lifecycle APIs are Experimental. Phase 12G read-only
inspection, supported CLI consumption, and visibility-safe Chie/Hantei/Oshie
evidence are externally exercised by Phase 12H without changing this host. No
Stable API or production-readiness claim is made.
