# ADR 0136: Bounded Trusted In-Process Extension Host Lifecycle

- Status: Accepted
- Date: 2026-08-30
- Phase: 12F

## Context

Phase 12E produces deterministic ordinary PHP wiring for one exact admitted
extension set and grant plan, but deliberately neither loads nor executes it.
The trusted/in-process profile therefore needs a narrowly governed runtime
boundary that can bind one exact generated file, activate extension lifecycle
objects, isolate operation state, and preserve failures without introducing a
general plugin runtime.

Trusted/in-process PHP has the full technical power of the current process.
Capability provider edges constrain only the objects deliberately supplied by
the application; they are not a sandbox and cannot prevent other PHP-process
access.

## Decision

Create Experimental `kongono/extension-host`, depending only on API Metadata,
Diagnostics, Extension Composition, and PHP. The package loads one caller-
selected absolute local ordinary file only after binding it to the exact
`GeneratedExtensionWiringArtifact`, exact `ExtensionGrantPlan`, content-addressed
basename, bytes, classes, accessors, implementation list, and lifecycle
interfaces. It performs one `require` after the pre-load checks. A mismatch
found after that point fails visibly; the loader does not pretend that PHP can
unload already declared classes and does not search, select, retry, or fall
back to another file.

Phase 12F adds lower generated application and operation boundary interfaces in
Extension Composition. Generated assemblies implement those interfaces while
preserving the existing typed `start()` and `beginOperation()` wiring. Hosted
entry methods validate exact ordered provider lists and delegate directly to
the typed methods. Ordered extension accessors expose only the constructed
lifecycle objects.

Application extensions implement `ApplicationExtensionInterface::start()` and
`stop()`. Operation extensions implement `OperationExtensionInterface::begin()`
and `close()`. Constructors establish ordinary object state but do not report
lifecycle success. Cleanup applies only after the corresponding lifecycle
method returned successfully; Kongono does not fabricate cleanup for a
constructor or lifecycle call that failed before reporting success.

`TrustedExtensionHost` starts application extensions in generated order and
rolls back or shuts them down in reverse order. Each `beginOperation()` creates
fresh generated operation state, begins extensions in order, owns exactly one
host lease, closes successful extensions in reverse order, releases retained
references, and releases the lease exactly once. Sequential, overlapping, and
reentrant operations share only the explicit application assembly; operation
assemblies and operation extension instances are never retained by the host.

Shutdown while leases remain fails without changing lifecycle state or running
cleanup. Operation activation or cleanup uncertainty retires the host: new
operations are rejected, while explicit application shutdown remains
available. Shutdown and operation close are once-only. Destructors perform no
lifecycle work.

When a primary failure and cleanup failures coexist, the primary throwable
remains the primary failure and cleanup throwable identities remain available
through the bounded lifecycle exception chain. With no primary failure, one
cleanup failure is rethrown unchanged; multiple cleanup failures use the fixed
combined lifecycle exception. Cleanup continues after each failure.

Reflection is permitted only in the loader's one-time exact shape validation.
Start, operation, close, and shutdown use direct typed calls and no Reflection,
registry, lookup, dispatcher, resolver, container, or ambient current host.
Diagnostics expose fixed Safe violation tokens and counts only; paths, class
names, generated bytes, plan identities, credentials, and native exception
messages are not copied into presentation.

## Consequences

- The production graph becomes 62 packages and 220 acyclic local edges.
- Exact generated evidence becomes stale when the hosted boundary implementation
  changes, because those lower interface and emitter bytes participate in the
  Extension Composition implementation identity.
- Loading is intentionally irreversible inside the current PHP process.
- Applications own provider instances, the exact artifact and plan, the file
  path, startup, operation boundaries, shutdown, and process isolation choices.
- The host is bounded lifecycle infrastructure, not authorization, security
  enforcement, a capability registry, a marketplace, or a production sandbox.

## Rejected alternatives

- Directory scanning, newest-file selection, Composer probing, autoload
  discovery, aliases, fallback files, or arbitrary callback dispatch.
- Runtime constructor Reflection, dynamic service location, ambient containers,
  mutable registries, hidden autowiring, or generated `eval`.
- Claiming that capability ports sandbox trusted PHP.
- Destructor-driven cleanup, silent post-require recovery, retry after partial
  activation, or discarding cleanup failures.
- Integrating Kernel, Security, Application Graph, Console, Observability,
  Chie, Hantei, Oshie, marketplace, distribution, or external execution.

## Deferred work

Phase 12G may add bounded read-only inspection and separately governed CLI and
developer-intelligence consumption. It is not implemented by Phase 12F.
