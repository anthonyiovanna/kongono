# ADR 0152: Exact-Current Single-Profile Model-Invocation Application Workflow

- Status: Accepted
- Date: 2026-09-01
- Stability: Experimental implementation boundary

## Context

Phases 14B through 14D provide neutral invocation values, deterministic plan
evidence, and a bounded runtime over one directly supplied adapter. They do not
define a supported application-owned path for binding one exact plan to
deterministic wiring and one terminal runtime operation. Phase 14E is an
independent inert reduction from a completed eligible runtime result to Agent
proposal evidence; it is not application startup, invocation authority, or an
execution port.

Applications need a small fail-closed workflow without adding provider
selection, credential discovery, ambient lookup, retry, retained sessions, or
authority semantics.

## Decision

Implement the optional Experimental `kongono/model-invocation-application`
package as an outer leaf depending only on PHP, API Metadata, Diagnostics, the
Phase 14B contract, Phase 14C build package, and Phase 14D runtime.

The package accepts exactly one explicit `InvocationPlanSource` and the exact
artifact bytes for that source. Its profile factory delegates currentness to
the Phase 14C validator and binds the verified plan, invocation, model profile,
adapter, artifact, source, and request identities into one immutable profile.
The application-profile identity hashes a versioned, canonical, LF-terminated
projection containing only bounded non-secret evidence.

The generator emits deterministic strict PHP for that profile. Generated bytes
use UTF-8 without BOM, LF endings, one final LF, fixed declaration order, and a
content-addressed identity. Structural validation and caller-relative
exact-current validation are separate. Publication is contained beneath one
explicit existing application root, atomic, initial-only, no-clobber, and
idempotent for identical bytes. Loading accepts one explicit file, snapshots
and reverifies it, requires only the fixed generated boundary, and returns a
one-use handle. It performs no directory scan or newest-file selection.

Starting the loaded handle requires one directly supplied `InvocationAdapter`
whose identity exactly matches the profile before adapter activity. One
application instance transitions `ready` to `active` to `retired`, constructs
one `InvocationRuntimeRequest`, delegates to one fresh
`ModelInvocationRuntime`, and returns the exact `InvocationRuntimeResult`.
Receipt identity, cancellation, and monotonic clock remain explicit run input.
Reentrancy, overlap, replay, and a second operation fail before another adapter
effect. Phase 14D remains sole owner of an opened session and cleanup.

Phase 14E is not a dependency and is never called. A caller may separately pass
an eligible returned result to that bridge after this workflow finishes.

## Disclosure and failure contract

Raw messages, prompts, model responses, action arguments, credentials, bearer
tokens, endpoints, headers, artifact bytes, generated PHP, and foreign failure
messages are excluded from identity projections and deterministic failure
text. Diagnostics `KGN-MODEL-APPLICATION-1430` through `1436` use closed finite
Safe context. Native-compatible exception construction preserves an exact
previous throwable where required; it does not claim native trace-argument
erasure.

Generated wiring is inert evidence. Trusted generated and in-process PHP are
not sandboxed. Profiles, plans, adapters, results, receipts, usage/cost claims,
suggestions, wiring, and digests do not authenticate, authorize, grant, execute
an Agent capability, establish external truth, or prove an effect.

## Consequences

Applications receive one supported deterministic single-profile path and must
continue to own plan creation, artifact placement, adapter construction,
cancellation, clock, and receipt identity. They also own any separate explicit
Phase 14E bridge call.

There is no provider SDK or first-party adapter, provider/profile/adapter
registry, default or discovery, credential discovery, automatic retry or
fallback, second profile, CLI, retained session, background work, deployment,
Graph/inspection/telemetry integration, or Phase 13 authority port. Kongono
remains usable without AI, a provider, credentials, an account, or a network.

Phase 14G and Phase 14H remain planned and separately governed.
