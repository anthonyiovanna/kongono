# ADR 0069: Generated Typed Wiring and No Runtime Service Location

- **Status:** Accepted
- **Date:** 2026-08-23
- **Phase:** 5A

## Context

The current Experimental `kongono/dependency-injection` package validates
explicit runtime definitions and constructs a fresh object on every dependency
edge. It supplies useful deterministic foundation behavior, but it is not a
supported generated application assembly, lifetime system, compiled container,
or application build workflow.

Phase 5 needs a preferred production wiring direction that removes dynamic
resolution and discovery from the request path without hiding dependencies or
turning a container into an application API.

## Decision

### Generated ordinary PHP

The preferred future production wiring mechanism is generated ordinary PHP
that contains explicit constructor calls and dependency edges. Generated wiring
must be readable, inspectable, statically analyzable, and compatible with
OPcache or preload where the host supports them.

Constructor injection remains the default. Dependency contracts, bindings,
lifetimes, and roots must be explicit build inputs. Canonical symbol spelling is
required; aliases, case normalization, silent substitution, and magic fallback
binding are not accepted.

The accepted performance statement is limited: after a successful build,
dynamic resolution and discovery are removed from the request path. Kongono
does not claim zero overhead, fastest performance, or superiority over another
framework. Later implementation must measure generated wiring against the
current resolver before making a performance claim.

### Explicit lifetime and cleanup ownership

Later phases must prove exact application-lifetime, operation-lifetime, and
transient-lifetime semantics before those names become runtime API. An object
requiring release must have explicit cleanup ownership and deterministic
reverse-order release. Lazy construction, if separately accepted, must use an
explicit typed generated factory or proxy with complete lifetime, failure,
cleanup, and concurrency semantics and measurable benefit.

### Rejected runtime mechanisms

The supported production path rejects:

- global, static, ambient, thread-local, or fiber-local service containers;
- passing a general resolver or container into application services;
- runtime service location by string or class name;
- property hooks that resolve or fetch dependencies when read;
- request-time reflection, classpath scanning, attribute scanning, or
  autowiring;
- hidden constructor inference from reflection;
- runtime `eval`, generated closures assembled from untrusted text, or remote
  generated code;
- magic fallback binding, silent aliasing, or case normalization;
- a mutable process-wide registry; and
- lazy resolution with implicit lifetime, cleanup, failure, or concurrency
  behavior.

PHP property hooks may still enforce local class invariants or value behavior
when separately appropriate and proved. They are not Kongono's dependency
resolution mechanism.

### Declarations and provenance

Phase 5A selects no declaration syntax, schema, PHP attribute, configuration
format, package, or public API. A later frontend is acceptable only if it
compiles into one canonical explicit composition input. If attributes are ever
accepted, they are build-time declarations only and cannot authorize runtime
discovery or make reflection-inferred dependencies authoritative.

Generated bytes are derived evidence rather than authoritative source. Their
identity must bind to exact validated input state. Generated source must not
contain secrets, credentials, environment values, request data, rejected input,
or Protected diagnostic values. Missing, stale, partial, mixed-version, or
unverifiable output must fail closed before work is accepted.

### Relationship to current Dependency Injection

`kongono/dependency-injection` remains the current narrow Experimental runtime
resolver. Its explicit definitions, deterministic validation, and
transient-per-edge construction are unchanged. Phase 5A does not replace,
deprecate, wrap, integrate, or alter it. A later phase must implement and prove
a separate generated boundary before production wiring can move away from the
current resolver.

## Consequences

Future production wiring will be reviewable as ordinary PHP instead of hidden
behind runtime service lookup. Static tools can inspect constructor edges, and
production requests avoid discovery and dynamic resolution after a successful
build.

The approach requires deterministic generation, exact invalidation, more
explicit lifecycle contracts, and generated-output review. Those obligations
are preferable to ambient lookup and request-time magic.

## Rejected alternatives

- Keeping the runtime resolver as the preferred production request-path
  assembly mechanism.
- PSR-11 or another general service locator exposed to application services.
- Reflection-inferred autowiring or attribute scanning at request time.
- Property-hook service acquisition.
- Mutable container registration after startup.
- Generated opaque binaries or unreadable closure graphs.
- Unsupported claims of zero cost or universal performance superiority.

## Explicit non-goals

This ADR implements no generator, compiled container, proxy, factory, lifetime
API, declaration frontend, schema, cache, Composer script, package, or runtime
integration. It defines no Application Graph relationship and begins no Phase
5B work.
