# ADR 0085: Generated Data Application and Operation-Owned Sessions

- **Status:** Accepted
- **Decision type:** Phase 6G implementation boundary
- **Stability:** Experimental APIs, workflow, runtime profile, and skeleton

## Context

ADR 0084 provides exact compile-time mapping evidence and generated typed Data
Mappers and repositories, but deliberately provides no production load boundary,
composition provenance binding, operation session ownership, or supported data
application workflow. ADRs 0068–0076 already provide deterministic composition,
ordinary generated PHP wiring, exact-current loading, leases, and reverse cleanup.

## Decision

Phase 6G adds the outer Experimental `kongono/database-application` package.
The package depends inward only on API Metadata, Composition, the neutral
Database contract, Database Mapping, and Diagnostics. No inward package depends
on it, and it selects no provider or dialect.

The explicit workflow builds the current mapping artifact, generates and
publishes mapping/data-access output, validates and loads that output, and only
then invokes the accepted Composition workflow. This order lets Composition
reflect the generated repository constructor and bind the exact generated PHP
file in its symbol-source provenance. Both workflows reverify captured files.
Build publishes only immutable content-addressed files; check writes nothing.

`OperationDatabaseSession` receives an explicit application-lifetime
`DatabaseConnector`, opens exactly one session during construction, delegates
the neutral session contract, and becomes permanently unavailable when close
begins. Generated reverse cleanup calls close once. Cleanup failure remains
transparent to the generated lifecycle composer, and the wrapper is never
retried or reused.

The data runtime profile accepts no application roots and exactly one public,
non-static, zero-argument `operationRoot1` whose non-null named return type
implements the marker-only `DataOperationRoot`. Profile validation precedes
startup. Each `beginOperation()` owns one generated operation boundary and root;
close releases both references. Application shutdown retains the accepted active
lease refusal and primary-plus-cleanup failure ordering.

The separate `skeletons/data-minimal` template is copy-once and optional. It
contains one record, one mapping source, one composition source, one generated
repository, one operation root, deterministic build/check scripts, an explicit
PostgreSQL 17 compiler service, and an explicit host-supplied connector input.
It does not change the existing web skeleton.

## Security and lifecycle consequences

Generated data access is loaded only from a caller-selected contained ordinary
file after exact-current structural validation, exact filename validation,
pre-load collision rejection, unchanged-snapshot reverification, and post-load
declaring-file and public-surface checks. Generated text cannot select another
file, trigger autoload fallback, or expand authority.

Sequential and overlapping operations receive distinct roots, repositories,
session wrappers, and provider sessions. No ambient connection, transaction,
container, registry, pool, retry, runtime mapping Reflection, discovery, scan,
proxy, or lazy I/O enters the runtime.

Diagnostics expose only closed package-owned categories. They exclude
credentials, DSNs, hosts, database/user values, SQL, parameters, records,
source/artifact/generated bytes, absolute paths, provider messages, classloader
state, stack arguments, and topology.

## Rejected alternatives

- Loading generated output before exact-current validation or by newest-file,
  scan, glob, mutable pointer, autoload fallback, retry, or `eval`.
- Application-shared sessions, ambient current connections, pools, reconnect,
  automatic transactions, or automatic retry.
- Runtime mapping Reflection, record discovery, ORM, Active Record, identity
  maps, units of work, relations, proxies, or hidden lazy loading.
- Moving provider selection into the integration package or moving database
  lifecycle into Kernel, HTTP, the resolver, or Application Graph.
- Adding database capability to the existing minimal web skeleton.

## Non-goals

Phase 6G adds no migration startup, schema sync, framework CLI, listener,
deployment surface, jobs, queues, events, auth, telemetry, another provider,
performance baseline, Stable API, production-readiness claim, checkpoint,
staging, commit, or Phase 6H behavior.
