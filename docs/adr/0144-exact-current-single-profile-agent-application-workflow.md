# ADR 0144: Exact-Current Single-Profile Agent Application Workflow

- Status: Accepted
- Date: 2026-08-31
- Phase: 13F

## Context

Phases 13B through 13E separate neutral Agent Principal values, deterministic
declaration evidence, inert admission evidence, and one provider-neutral
synchronous runtime. Applications still need one supported outer workflow that
can bind those exact inputs, publish and load ordinary generated wiring, and
own operation collaborators until the existing runtime accepts cleanup
ownership.

That boundary must not turn identity or generated bytes into authority, invent
a profile registry, select a provider, discover tools, or conceal application-
owned authentication, authorization, revocation, and currentness duties.

## Decision

Kongono adds the opt-in Experimental `kongono/agent-application` package. It
supports exactly one immutable profile form: one explicit exact-current
declaration artifact paired with one explicit matching admitted authority plan.
Profile construction rebuilds the declaration and exactly reconciles artifact
identity and digest, principal, ordered capability declarations and
requirements, constraints, ordered evidence references, and every admission
decision. Denied required capability or any mismatch fails closed before
generated loading or effect.

The package deterministically emits bounded strict PHP for the exact profile
and fixed package implementation. Generated bytes are LF-only, have no BOM,
are content-addressed, and omit raw declaration, authorization, prompt,
provider, capability, credential, and secret content. Structural validation
proves canonical syntax and fixed interface/class/method shape independently
of caller-relative exact-current validation, which regenerates from the exact
current profile and implementation.

Publication accepts only one explicit existing application-owned root and a
strict contained output location. It rejects root-equal, outside-root, linked,
reparse, alternate-stream, changing, partial, and conflicting targets. Equal
bytes are idempotent; different existing bytes are never overwritten. Loading
accepts one explicit exact path, snapshots and validates it, rejects class
collision, loads only the fixed boundary, and reverifies the snapshot before
returning a handle that may start once. It performs no proposal or capability
effect on load and never scans or chooses a newest artifact.

The workflow has two explicit operations. `build()` reconstructs the exact
declaration artifact, profile, and generated bytes before contained publication
and exact loading. `check()` repeats the same proof without writes and requires
the exact expected output already to exist unchanged.

One started application accepts all proposal, capability, currentness,
cancellation, clock, intent, operation, and budget collaborators explicitly for
each operation. It owns accepted proposal and capability ports while validating
the runtime request. Any pre-runtime failure closes capability ports in reverse
order and the proposal port last, attempting all cleanup and preserving primary
and cleanup throwable identities separately. Once the Agent Runtime accepts the
request, cleanup ownership transfers exactly once and the application performs
no second close.

At most one synchronous operation is active per application. Reentrant or
overlapping work is refused before a second effect. Sequential operations and
separate applications share no mutable operation state. Idle close is terminal
and idempotent, active close is refused without false closure, and post-close
operation attempts still clean newly supplied ports. Runtime results and
receipt meaning are returned unchanged.

Declaration artifacts, authority plans, profiles, generated identity, and
loaded wiring remain evidence rather than authentication, authorization,
credentials, reusable grants, or perfect external-effect truth. The caller
continues to own external authority currentness, and Phase 13E checks its
explicit currentness port immediately before possible effects.

## Security and lifecycle consequences

Trusted generated PHP and trusted in-process PHP are not sandboxed. The package
adds no provider or model SDK, endpoint, credential mechanism, network,
environment, global, registry, resolver, container access, dynamic discovery,
Reflection discovery, hot reload, command, skeleton, marketplace, remote agent
service, deployment manager, memory, retained session, store, queue, worker,
scheduler, retry, delegation engine, autonomous loop, parallel operation,
Graph, inspection, or developer-tool authority.

Only explicit ports may perform effects, and the existing Agent Runtime remains
responsible for currentness, cancellation, budgets, proposal validation,
capability invocation, receipts, and runtime-owned cleanup. Package diagnostics
are fixed and non-disclosing. Primary and cleanup failures retain their exact
throwable identities without exposing unsafe values through presentation.

## Dependency and compatibility consequences

`kongono/agent-application` depends only on PHP, Agent Admission, Agent
Declaration Build, Agent Principal Contract, Agent Runtime, API Metadata, and
Diagnostics. No existing production package depends on it, and no existing
production PHP changes. The graph is 68 acyclic production packages and 250
local production dependency edges. PHPUnit remains its sole development
dependency. No API is Stable.

## Alternatives rejected

- A registry or active-profile selector would introduce unapproved ambient
  selection policy and a second application shape.
- Handwritten application wiring would lose exact deterministic identity and
  reproducible currentness proof.
- Loading by scan, directory order, timestamp, or newest file would make
  currentness ambiguous.
- Giving generated code proposal or capability collaborators would make load a
  potential effect boundary.
- Letting both application and runtime close accepted ports would introduce
  double cleanup and obscure failure identity.
- Provider-specific adapters, retained sessions, background work, and broad
  automation belong outside this phase.

## Current boundary

Phases 13A through 13F are current. Phase 13G visibility-safe inspection and
Phase 13H external acceptance remain planned and require separate authenticated
directives. Kongono remains usable without AI, a provider, an account, or a
network.
