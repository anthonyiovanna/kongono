# ADR 0088: Operation-Scoped Identity, Change Tracking, and Transaction Authority

- **Status:** Accepted
- **Decision type:** Phase 7A identity, lifecycle, change, relationship, and transaction authority
- **Stability:** Architectural direction for an Experimental, pre-1.0 capability

## Context

A persistence context can coordinate object identity, snapshots, changes, and
database writes, but those responsibilities create persistent-runtime,
concurrency, disclosure, and failure risks. Process-global identity maps retain
application objects across operations. Implicit flush or transaction ownership
hides database effects. Unbounded cascades and relationship traversal conceal
destructive scope. A failed write can leave both database and in-memory state
uncertain.

Phase 6 already assigns database sessions and transactions to explicit operation
owners, uses reverse cleanup, and preserves a primary failure together with
cleanup failure. Phase 7 must build above those rules without widening authority.

## Decision

Every future persistence context, identity map, loaded-object registry, snapshot,
change set, or repository session is operation-scoped. None may be static,
request-global, process-global, shared at application lifetime, or reused after
close. An identity map may guarantee one in-memory object identity only inside
one explicit operation and context. That guarantee provides no cross-operation
identity, cache, authorization, ownership, or distributed consistency.

Context retirement is exact. Closing or a terminal failure first makes the
context reject new work and retires its identity, snapshot, change-set, loaded-
object, and repository-session state before any fallible underlying resource
release. Cleanup then proceeds in accepted reverse ownership order. A cleanup
failure cannot reactivate the context or obscure the primary failure; both are
retained under the accepted primary-plus-cleanup ordering. Every later use of a
closing, closed, terminal, or uncertain context must fail visibly. Persistent
workers must retain no operation-owned domain reference after retirement.

Changes remain explicit. Later APIs may define new, managed, or removed state
and deterministic metadata-generated change sets, but changing an in-memory
object alone performs no persistence I/O. No destructor, response completion,
shutdown handler, property access, arbitrary method call, interceptor, proxy,
aspect hook, or implicit event listener may auto-flush. `flush` remains an
explicit caller action with an explicit reviewable result.

The caller retains transaction authority. A persistence context consumes an
explicit operation-owned Database executor and transaction contract. It must not
silently begin, commit, roll back, retry, reconnect, replay, or widen isolation.
A later workflow helper may compose explicit policy only under separate
authority. If a flush, concurrency check, or provider action leaves database or
in-memory state uncertain, the context enters a terminal uncertain state, fails
closed, and performs no automatic replay.

Persist and remove cascades require explicit bounded metadata and later review.
Database foreign-key actions remain schema/database authority and are distinct
from object-graph cascade policy. Orphan removal, bulk mutation, destructive
scope, and multi-aggregate writes need explicit later contracts and safe
defaults. Phase 7A selects no cascade.

Stable entity identity, new-versus-existing state, identity-generation
authority, and version or concurrency tokens must be explicit and type-safe.
Optimistic concurrency failure must be distinguishable from absence and provider
failure without disclosing private values. Phase 7A selects no ID type,
composite-key model, generator, column, token format, or conflict-resolution
policy.

Persistence diagnostics remain package-owned, bounded, actionable, and
presentation-neutral. They must exclude credentials, connection material, SQL,
parameters, entity or value data, relationships, identity or version values,
snapshots, change sets, source/artifact/generated bytes, absolute paths, provider
messages, stack arguments, and application topology.

## Consequences

- Persistence state and domain references cannot leak across operations.
- One-context identity is a bounded lifecycle property, not authorization or a
  distributed cache guarantee.
- Callers can identify when persistence I/O and transaction decisions occur.
- Terminal and uncertain failures remain visible and prevent unsafe context
  reuse or replay.
- Cascades, deletion behavior, identity forms, and conflict policy remain open
  for later authenticated decisions.
- Phase 7A creates no runtime context, identity map, change tracker, transaction
  helper, diagnostic identifier, or public API.

## Rejected alternatives

- Static, application-shared, process-global, or reusable persistence contexts
  and identity maps.
- Automatic flush at destruction, response completion, shutdown, property
  access, or arbitrary method calls.
- Hidden transaction begin, commit, rollback, retry, reconnect, isolation
  widening, or concurrency replay.
- Treating uncertain database or in-memory state as successfully synchronized.
- Implicit recursive cascades, orphan removal, bulk mutation, or multi-aggregate
  writes.
- Disclosing SQL, parameters, domain data, identity/version values, snapshots,
  change sets, paths, provider messages, or topology in diagnostics.
