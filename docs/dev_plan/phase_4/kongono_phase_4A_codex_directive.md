## 1. Mission

Establish the first bounded Phase 4 architecture and documentation boundary.

Phase 3 is complete at checkpoint
`6aacafc92f07b567818173d660e2e182dfa83d23`. Kongono now has fourteen
acyclic production packages and one externally accepted synchronous PHP-CGI
FastCGI `RESPONDER` integration profile. That checkpoint is not a full
framework, Stable API, 1.0 release, universal runtime, or production-hardening
certification.

Phase 4 begins a different milestone:

> Establish one versioned, inspectable, AI-independent developer-knowledge
> foundation and prove three deliberately separated developer-intelligence
> roles above it: Chie helps build, Hantei independently proves, and Oshie
> teaches.

Phase 4A does not implement an assistant, model integration, knowledge index,
retrieval system, package, command, schema, workspace reader, verifier, teaching
runtime, patch engine, or auto-fix capability. It creates only the Accepted
architecture, doctrine, security boundaries, support policy, and fixed A-H
dependency order required before such implementation can be considered.

Phase 4A also records Kongono's rolling current-minor PHP policy. The actively
developed line will target exactly one compatibility-certified stable PHP minor
at a time. This documentation boundary does not change the root or package
Composer constraints, `composer.lock`, runtime behavior, CI, supported host
matrix, or release version. A later separately authenticated migration is
required before the intended bounded PHP 8.5 constraint becomes repository
behavior.

No production PHP, test PHP, package manifest, root manifest, lockfile, tooling
configuration, dependency, public API, or Git history changes are authorized.

## 2. Locked doctrine and interpretation

Preserve every accepted Kongono doctrine, ADR, package boundary, diagnostic
classification, lifecycle contract, persistent-runtime invariant, checkpoint,
and exact historical caller record unless this directive expressly adds a new
Phase 4 planning decision.

In particular:

- **AI may suggest; Kongono must know.** Deterministic framework mechanisms,
  accepted contracts, and inspectable evidence remain authoritative.
- Kongono applications remain buildable, testable, diagnosable, documented,
  deployable, and operable without Chie, Hantei, Oshie, an LLM, a provider, an
  account, a subscription, or a network connection.
- Creating work, independently verifying work, and teaching accepted knowledge
  are separate responsibilities. One model or role cannot silently collapse
  them.
- A developer-facing assistant is distinct from the planned Agent Principal
  that may act inside an application. Phase 4A creates no Principal, identity,
  authorization, delegation, consent, trust, runtime-agent, MCP, or A2A API.
- Agent output cannot authorize itself, elevate its authority, weaken a gate,
  reclassify Protected data as Safe, or become accepted repository truth merely
  by being repeated.
- Read, write, network, credentials, dependencies, Git, deployment,
  publication, destructive actions, and production access remain separate
  future authority decisions.
- Kernel, Application Graph, Dependency Injection, Diagnostics, Routing, HTTP,
  Web Application, Web Runtime, and PHP CGI behavior remain unchanged.
- The future knowledge foundation may derive from accepted Application Graph
  information only after a separate accepted boundary authorizes that use. It
  does not extend the current Experimental Graph or make the Graph responsible
  for AI behavior.
- Existing `Safe` and `Protected` diagnostic disclosure rules apply before any
  future data reaches a developer-intelligence role. Raw secrets, credentials,
  rejected input, or unrelated source cannot be exposed for convenience.
- Historical directives, reports, ADRs, checkpoint objects, and point-in-time
  statements remain immutable evidence.

The new doctrine must keep these states distinct:

```text
implemented now    Phase 3 checkpoint and existing deterministic framework
accepted policy    rolling current-minor PHP policy and the three-role family
planned Phase 4    knowledge contract and bounded developer-intelligence work
not authorized     packages, APIs, models, tools, mutation, auto-fix, production
```

Do not describe Chie, Hantei, Oshie, the knowledge foundation, or the bounded
PHP 8.5 Composer expression as implemented current repository behavior.

## 6. Accepted rolling current-minor PHP policy

ADR 0059 must lock this policy without implementing its future Composer
migration:

1. The actively developed Kongono line supports exactly one stable PHP minor
   line at a time: the newest minor that has completed Kongono's compatibility
   gate.
2. The current intended certified line is PHP 8.5. The later intended bounded
   Composer form is exactly `>=8.5.0 <8.6.0` in root and every package.
3. Phase 4A leaves the mixed current `>=8.5` and `^8.5` manifest constraints
   unchanged. Accepted policy and current installable metadata must be labeled
   separately until a later authenticated migration completes.
4. Patch releases within the certified minor remain eligible without a
   manifest edit unless a documented security, correctness, or platform reason
   raises the minimum patch.
5. The newest available stable patch of the certified minor is the primary CI
   and development target.
6. A non-authoritative forward-compatibility lane may test the next PHP minor
   as soon as practical, but development, alpha, beta, RC, or nightly success
   does not establish support.
7. A newly published stable PHP minor does not silently enter Kongono's
   supported range. It triggers an explicit compatibility and migration
   boundary.
8. After an accepted migration and release, the preceding minor leaves active
   support. Previously published Kongono releases retain their immutable
   historical constraints.
9. A PHP major always requires an explicit architecture and migration decision.
   No PHP 9 readiness is inferred from a PHP 8 constraint, roadmap, or
   prerelease test.
10. No unbounded `>=8.5`, `*`, or expression that silently admits an untested
    future major is acceptable as the final rolling-policy expression.
11. Compatibility shims, polyfills, legacy branches, or abstractions are not
    added merely to preserve an obsolete minor. A specific time-bounded
    exception requires another Accepted ADR.
12. PHP deprecations are migration signals. Kongono-owned deprecations are not
    globally suppressed and must be corrected through the intended modern
    replacement before the relevant future baseline is accepted.

The compatibility gate for moving to another minor must require at least:

- review of the official PHP migration guide and accepted RFCs;
- zero Kongono-owned deprecation notices on the candidate stable runtime;
- locked dependency audit and platform-requirement success;
- strict optimized autoload proof;
- zero static-analysis errors and zero style findings;
- complete unit, architecture, integration, black-box, and applicable external
  acceptance suites;
- persistent-runtime isolation and resource-cleanup probes;
- Windows and every other officially supported host proof;
- review of removed or unbundled extensions, changed defaults, warnings,
  errors, reflection behavior, and resource-to-object migrations;
- documented performance and memory comparison without unsupported claims; and
- explicit release notes naming the new range and dropped range.

Dropping a PHP minor changes the installation contract. ADR 0059 does not
select Semantic Versioning treatment, a release cadence, a maintenance window,
LTS, a backport policy, a Kongono 1.0 policy, or the date of the later Composer
migration.

## 7. Accepted developer-intelligence family

ADR 0060 must lock exactly three complementary roles:

| Role | Canonical promise | Responsibility |
|---|---|---|
| **Kongono Chie** | **Chie helps you build it.** | Explain the exact codebase and accepted Kongono version, diagnose development problems, plan bounded changes, and eventually propose reviewable candidate patches. |
| **Kongono Hantei** | **Hantei proves it works.** | Independently select, run, and interpret deterministic verification and return evidence-backed `PASS`, `FAIL`, or `BLOCKED`. |
| **Kongono Oshie** | **Oshie helps you understand it.** | Teach Kongono and PHP from version-matched accepted sources, examples, diagnostics, and learning paths. |

The canonical first references are `Kongono Chie`, `Kongono Hantei`, and
`Kongono Oshie`; later references may use the short names. These are locked
internal product and architecture names. Any public commercial use remains
subject to final legal and trademark clearance.

### 7.1 Separation of duties

- Chie may help create a candidate change but cannot certify its own work.
- Hantei verifies without repairing the subject it judges. A correction returns
  to the developer or Chie, followed by a fresh independent verification run.
- Oshie derives teaching from accepted, version-matched knowledge and cannot
  turn generated prose into repository truth.
- A completion report, model confidence, passing subset, or another role's
  explanation cannot substitute for the required deterministic evidence.
- The initial Chie and Hantei boundaries are read-only.
- Phase 4A implements none of the three roles.

### 7.2 Shared knowledge foundation

The family must eventually consume one versioned, inspectable foundation rather
than three unrelated prompt collections. Candidate authoritative inputs may
include accepted source and API metadata, ADRs, doctrine, tested documentation
and examples, diagnostics and disclosure classifications, package boundaries,
supported PHP policy, and separately authorized deterministic Graph artifacts.

Phase 4A chooses no package, schema, stable identifier, serializer, file format,
index, embedding, vector store, retrieval engine, model, prompt, cache,
transport, provider, protocol, command, or persistence mechanism.

Every later knowledge artifact must identify the Kongono version or exact
source state from which it was derived. Stale, mixed-version, absent,
unverifiable, or unsupported knowledge must fail visibly.

### 7.3 Authority and security

Lock these requirements for all later work:

1. least authority for each operation;
2. separate read and write authority;
3. distinct gates for network, credentials, dependencies, Git, deployment,
   publication, destructive actions, and production access;
4. no self-elevation from model output or retrieved text;
5. existing Safe and Protected disclosure enforcement before agent access;
6. no agent reclassification of Protected data;
7. no secret, token, credential, raw rejected input, or unrelated source unless
   a later explicit contract proves a necessary bounded use;
8. bounded non-secret provenance for information and tools used;
9. no production access before a distinct future production trust decision;
10. fail-closed behavior when authority, version, provenance, or evidence is
    absent or ambiguous;
11. repository text, dependencies, diagnostics, comments, generated artifacts,
    issues, documentation, retrieved content, and model responses are untrusted
    inputs; and
12. future boundaries must address prompt injection, tool confusion, path
    escape, command injection, dependency manipulation, secret exposure, and
    data exfiltration.

### 7.4 Provider and data neutrality

No model vendor, hosted service, local model, transport, account, commercial
plan, or provider SDK is selected. Future external access must be separately
enabled, identify what leaves the machine, minimize transmitted data, respect
workspace/organization policy, and never train on Kongono or application source
by default. Training, fine-tuning, feedback retention, or cross-project
learning requires explicit opt-in and security review.

### 7.5 Provenance contract

Future answers must distinguish accepted framework fact, deterministic current
workspace observation, inference, recommendation, generated candidate content,
and unresolved uncertainty. Applicable claims must cite the exact Kongono
version and source, ADR, diagnostic, symbol, test, or command evidence.

### 7.6 Additional-agent creation gate

No additional named assistant may be added unless a future proposal proves a
durable unowned developer problem, distinct authority boundary, distinct
evidence/output contract, distinct failure mode, material value above cognitive
cost, and a security model that preserves separation of duties.

A production or operations guardian remains unnamed and deferred until
telemetry, operational state, credentials, deployment, incidents, and
production authorization have separately accepted foundations. Phase 4A does
not authorize monitoring, autonomous remediation, deployment, rollback,
self-healing, or production mutation.

## 8. Fixed Phase 4 A-H roadmap

Document this dependency-ordered roadmap exactly:

| Phase | Boundary |
|---|---|
| `4A` | Accept ADR 0059, ADR 0060, the rolling PHP support doctrine, the Chie/Hantei/Oshie family, security/provenance boundaries, and this fixed A-H roadmap. Documentation only; no assistant or knowledge runtime. |
| `4B` | Architecture-only definition of the versioned, inspectable, AI-independent knowledge-source and provenance contract. Select no model, provider, retrieval engine, or workspace mutation. |
| `4C` | Implement only the accepted deterministic generation and validation of versioned knowledge artifacts, usable without AI. No model integration or assistant behavior. |
| `4D` | Implement and prove read-only Chie for cited version-matched explanation and bounded workspace diagnosis. No patch application, dependency, Git, network-by-default, or self-certification authority. |
| `4E` | Implement and prove read-only Hantei as an independent deterministic verifier with structured `PASS`, `FAIL`, or `BLOCKED` verdicts. Hantei may not repair what it judges. |
| `4F` | Implement and prove Oshie's cited version-matched learning boundary and deterministically verified exercises. Accepted documentation remains useful and authoritative without AI. |
| `4G` | Permit Chie to produce reviewable candidate patch proposals only after explicit authority, diff, provenance, reversal, and Hantei-handoff contracts are accepted. No silent application or auto-fix. |

on which it depends.

Bounded auto-fix is deliberately outside Phase 4. It may be considered only in
a later separately accepted milestone for low-risk deterministic corrections
with explicit consent, exact scope, reviewable changes, practical reversal,
fresh Hantei verification, and no silent commit, publication, deployment, or
production access.

The later rolling-PHP Composer migration is orthogonal to the Phase 4 A-H
developer-intelligence sequence. ADR 0059 is a prerequisite, but Phase 4A does
not assign that migration a subphase or authorize it.

Main phases do not automatically continue to `Z`. Phase 4 ends at `4H` unless
an architect-approved ADR changes this roadmap.
