# Application workflow engineering guide

## Use the supported boundary

Application tooling should call `ApplicationBuildWorkflow::build()` to publish current derived state and `ApplicationBuildWorkflow::check()` before loading it. Do not reproduce filename selection, publication, or validation in application code.

Both calls require the exact application root and a pre-existing output directory strictly inside that root. Build may publish content-addressed files. Check is read-only. Neither API creates directories, scans output, maintains a pointer, repairs state, or deletes old output.

## Command contract

The minimal skeleton owns only `app:build`, `app:check`, and `app:run`. Success output may contain fixed labels and lowercase SHA-256 identities. Failure output must be fixed and bounded. Never print exception messages, previous/native errors, stack traces, paths, source bytes, generated bytes, environment state, credentials, or secrets.

`app:run` must check before loading. It may invoke exactly one resolved installed PHP-CGI executable for one fixed local request. Its CGI snapshot uses the inert fixed query marker `kongono_proof=1` to retain command-line hardening behavior on the one-shot Windows executable; routing and application behavior must remain independent of that marker. Array-form process execution, bounded captured output, a sanitized child environment, disabled trusted presentation, and immediate exit are required. Never add `-b`, a socket, listener, port, watcher, supervisor, worker loop, or daemon behavior.

## Skeleton changes

Treat `skeletons/minimal/kongono.skeleton.json` as inert ownership metadata. Its sorted path inventory must match the template exactly. It contains no self-hash, timestamp, host path, or environment data.

Any template change requires tests for:

- exact inventory and Composer scripts/dependencies/autoload;
- exact Composition inputs, services, cleanup, and roots;
- the real route and exact 200/404 response bodies;
- build/rebuild content identities and retained old output;
- write-free check behavior and partial/stale/tampered rejection;
- mirrored path-package installation with plugins disabled;
- two isolated one-request CGI runs; and
- absence of generated output, mutable pointers, runtime reflection, service lookup, listeners, and deployment behavior.

Use fresh resolved external monorepo-shaped fixtures for destructive proof. Copy only the skeleton and lock-required local package roots. Remove only the narrowly owned temporary root in `finally`.

The root-owned implementation of this proof is
`composer acceptance:phase5`. Its public canonical JSON reports exactly 28
ordered PASS scenarios and deterministic content identities. Do not infer
acceptance from process exit alone: validate exact response and artifact bytes,
write sets, bounded raw failure streams, isolation, retirement, nondisclosure,
and cleanup. The command remains separate from `composer quality`.

## Upgrade rule

Copied source is application-owned. Do not implement an automatic skeleton upgrade, merge, overwrite, migration, or remote fetch. A later skeleton is adopted only through an explicit reviewed application diff.
